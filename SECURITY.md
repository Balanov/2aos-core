# Безопасность

## Сообщить об уязвимости

Не создавайте публичный issue с секретами, данными клиентов или эксплойтом. Напишите на `info@baiagent.ru` с описанием затронутой версии, условий воспроизведения и предполагаемого воздействия.

## Модель угроз и границы

- API ключи хранятся только как SHA-256 с domain separation; выводятся один раз при создании.
- Integration/payout конфигурации шифруются AES-256-GCM. Ключ на диске защищает от случайного раскрытия, но не от атакующего, уже получившего и БД, и ключ.
- Внешние URLs требуют явного origin allowlist; redirects запрещены. Не передавайте секреты в URL.
- ZIP декларативных агентов проверяется на traversal, symlink, дубли, CRC, размеры, compression ratio и подпись. Нативный код не исполняется в основном процессе.
- Approval digest связывает точное действие, но не доказывает личность человека. Аутентификация выполняется API key/RBAC.
- Outbox idempotency предотвращает повтор внутри retention/schema, но не отменяет уже произошедший внешний эффект.
- Audit hash-chain обнаруживает изменение записей, но не защищает от атакующего с полным контролем БД и алгоритма. Для независимого доказательства реплицируйте head hash в отдельный контур.
- K-порог и округление не гарантируют невозможность реидентификации. Не экспортируйте сырые тексты, документы, идентификаторы или редкие сочетания.
- LLM/VLM вход считается недоверенными данными. Для критичных действий обязательны правила, approval и независимая проверка авторитетного состояния.

## Production checklist

TLS, минимальные роли, отдельные worker sandboxes, allowlisted endpoints, подписанные пакеты, отключение development packages, backup key/SQLite, log redaction, rate limiting на proxy, мониторинг диска и регулярный restore drill.
